# 二、问题清单

## 问题 1（中高）：oracle 候选集在看到诊断数字之后改了两次，同分布五类的结论依赖第三版

证据 `run_validated.log`：oracle 阶段一共跑了三遍，都在同一个日志里。
第一遍（日志第 36–93 行）：网格只有 K = 1、8、32、64，没有扩展规则。同分布五类 K=64 时验证 0.0916，比 K=32 的 0.1040 好 12 %，按现行规则应扩展，但日志里没有"extend"一行，说明当时代码里还没有这条规则。第 73 行打印诊断 oracle = 0.109351，比 B 的 0.0943 还差。
第二遍（第 105–181 行）：加入"64 比 32 好 5 % 以上才扩到 128、256"的规则，第 149 行诊断 oracle = 0.094559，和 B 打平。
第三遍（第 190 行起）：再加入"按训练子类分簇"的候选，第 240 行诊断 oracle = 0.080230，比 B 好 14.9 %。中断发生在这一遍的单峰族。
每一遍里，挑哪个候选都只看验证集，这一点没问题。问题在于"候选集长什么样"是在诊断数字打印出来之后才改的，而改的方向恰好让同分布五类从"oracle ≈ B，像信息极限"变成"oracle 好 15 %"。
原文 `HANDOFF_A18-B2.md:64`："选择基于验证误差，未用诊断误差挑先验。"
原文 `HANDOFF_A18-B2.md:74`：把扩展规则写成既定设置。
这两句字面上成立，但没有交代三遍运行的顺序。读者会以为候选集是事先定的。
补充：两次修改都有验证集上的理由（验证误差还在明显下降），不一定是看诊断数字才改的（推测）。但没有事先登记，就没法区分。
同分布五类最终 oracle−B 的区间是 [−0.0319, +0.0045]，本来就跨零（已核实）。
建议：HANDOFF 第 2、3 节如实写三遍运行和各自的诊断数字；同分布五类的结论降为"按子类分簇的先验在验证集上好 19 %（0.0716 → 0.0581），诊断集上方向一致但区间跨零"；在一个新的诊断种子上用定好的候选集再跑一次。

## 问题 2（中）：K 网格在 64 截断，oracle 没有饱和；"零件组合最像信息受限"依赖这个截断

扩展规则只看"64 比 32 是否好 5 %"。阶梯（2 %）、零件组合（K=32 反而比 K=8 差，不单调）、随机光滑（4 %）都没触发，停在 64（已核实：`oracle_candidates.csv`）。
我在沙盒里用同一个 `fit_prior`（KMeans random_state=18）重拟。K=64 时诊断误差与原结果逐位一致，说明复现可靠。再往上加（已核实，沙盒）：

| 谱族 | K | 验证 | 诊断 | 相对 B |
|---|---:|---:|---:|---:|
| 阶梯谱 | 64 / 128 / 256 | 0.1798 / 0.1785 / 0.1895 | 0.2069 / 0.2016 / 0.2156 | 128 时 −16.4 % |
| 零件组合 | 64 / 128 / 256 | 0.1693 / 0.1682 / 0.1648 | 0.1703 / 0.1606 / 0.1643 | 256 时 −9.0 % |
| 随机光滑 | 64 / 128 / 256 | 0.0655 / 0.0631 / 0.0599 | 0.0719 / 0.0720 / 0.0696 | 256 时 −14.9 % |

（相对 B 为推算；实际分量数因小簇剔除分别为 64/120/196、59/108/154、63/123/226。）
按"验证最小"来选，零件组合和随机光滑都会选 K=256。零件组合的 oracle−B 变成 −9.0 %，区间 [−0.0397, +0.0042]，仍跨零但更接近显著；随机光滑变成 −14.9 %，区间 [−0.0210, −0.0040]。
所以"零件组合最接近 oracle"有一部分是因为它的 oracle 被截断得最早。
另外，噪声下弱可辨能量比例也不支持把零件组合排成最信息受限：四个目标族里零件组合最低（16.35 %），阶梯最高（35.45 %）（已核实：`nullspace_metrics_complete_resume_v2.csv`）。HANDOFF 第 97 行自己也说这个比例不能单独判定。
建议：零件组合的结论改为"本轮 oracle 与 B 差距最小，但 oracle 未饱和，不能据此排成最信息受限"；K 网格改成"验证误差连续两档改进 < 1 % 才停"，事先写进 protocol。

## 问题 3（中）：oracle 的优势不全是"先验更好"；对照族的差距更大，HANDOFF 没解读

oracle 相对 B 有两项额外信息：
一是知道真族。HANDOFF 第 58、70、78 行写了。
二是知道噪声水平。oracle 的噪声协方差 `DEVCOV` 在 `a11_device.py:171` 按 P0 换算到单位面积坐标；单位面积谱的信号幅度固定，于是 oracle 等于知道 P = P0 时的信噪比。B 训练时功率在 0.5–2 P0 之间随机，输入先 L1 归一，不知道这个量。HANDOFF 第 70 行"不提供……亮度"不完全准确：亮度没有直接给，但通过噪声协方差隐含给了（推算：读代码）。影响多大没法单独量化（推测：白噪声相对信号不大时影响小）。
为了看"知道真族"占多少，我把六族的先验合成一个不带族标签的混合（每族权重 1/6），再算诊断误差（已核实，沙盒）：

| 谱族 | 真族 oracle 相对 B | 不知族（六族合并）相对 B | 不知族的区间 |
|---|---:|---:|---|
| 阶梯谱 | −14.2 % | −13.7 % | [−0.050, −0.016] |
| 零件组合 | −5.7 % | −2.3 % | [−0.022, +0.013] |
| 随机光滑 | −12.1 % | −8.5 % | [−0.014, −0.0003] |
| 同分布五类 | −14.9 % | −6.8 % | [−0.021, +0.009] |
| 单峰 60–200 nm | −70.7 % | −57.7 % | [−0.023, −0.014] |
| 宽带通 | −23.7 % | −22.6 % | [−0.019, −0.008] |

推算：阶梯谱的差距几乎不靠族标签；同分布五类约一半靠族标签，去掉后区间跨零；随机光滑约三成靠族标签。这里只合并了 6 族，B 面对的是 26 族，真实的判族难度更大，所以这张表对 oracle 仍偏宽松。
对照族：oracle 在单峰族上比 B 好 71 %，宽带通好 24 %，都比四个目标族的差距大（已核实）。这说明"oracle 比 B 好"在 B 的强族上也普遍成立，不是第六类特有的。用"oracle−B 差距"判断"哪一族还有先验空间"时，要和对照族比，而不是和零比。按这个尺子，第六类四族反而是 B 离 oracle 相对最近的几族（推算）。
建议：HANDOFF 第 1 节对照表后补一段解读；第 2 节随机光滑、同分布五类的"有先验空间"改为"有先验空间，但其中一部分来自知道真族"，附上不知族 oracle 的数字。

## 问题 4（中）："加大网络反而更差"是有限谱库过拟合，不是容量证据；单种子

原文 `HANDOFF_A18-B2.md:107`："更像专用化后的泛化或先验表达问题，不能把高训练误差统一叫'网络太小'。"这个方向对。
补充证据（已核实：`specialist_768x6_gap.csv`）：随机光滑 训练 0.0595、验证 0.0775、诊断 0.0971；512×4 是 0.0614、0.0706、0.0855。更大的网络训练误差更低、验证和诊断更差，是典型过拟合。
原因（推算）：每条谱被看到 2926 次，是 cnet0 的 4.1 倍。专用实验同时改了"族的组成"和"每条谱的重复次数"，没法分开。
所以这一组对照能说明的是"在 3000 条/族的固定谱库上专门训练，没有带来稳定收益"，不能说明"容量不是瓶颈"。HANDOFF 第 10 行"也没有证据证明单纯扩大 B 就能解决"措辞可以接受；但交给用户的一句话总结"加大网络反而更差"容易被读成容量结论。
建议：下一轮如果还要回答容量问题，至少做两件事：(a) 训练时每步现生成新谱（或把四族谱库扩到和 cnet0 同等遍数，约 5000 条/族 × 4 倍），去掉过拟合这个混杂；(b) 每个配置跑 3 个初始化种子，报告种子间标准差，再和成对区间一起看。

## 问题 5（低中）：四个目标族是在同一批诊断谱上挑出来的，B 在这些族上的误差偏高

"第六类"这四族来自 B1 在 VSEED+13 上的结果（A、B 都差的族）。B2 又在同一批谱、同一份噪声上比较 oracle、专用网络和 B（`run_networks.py:20–22` 逐位复现了 B1 的噪声流）。
按"在这批谱上差"挑出来的族，B 在这批谱上的误差有向上的偶然成分；换一批谱会往回落（推算：选择效应）。这会让 oracle−B、专用−B 的差距略偏大。
旁证（已核实）：同一个模型在验证集和诊断集上，诊断集普遍更难。oracle 同分布五类 验证 0.058、诊断 0.080；专用 512×4 同分布五类 验证 0.069、诊断 0.097，阶梯 0.196、0.225。验证集是选择用的，本身偏乐观，所以这条旁证只能说明两批谱差别不小，不能单独证明选择效应。
建议：在一个从未用过的新诊断种子上重跑评估段（oracle 用已存 prior、专用网络用已存权重，不重拟），约十几分钟。新种子先对照 R1 种子表查重。

未校正的 5000 次区间我用原种子 20261104 重算，与 CSV 一致（已核实）。
